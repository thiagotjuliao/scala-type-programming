## Exercício 01 — o tipo da linha a partir das colunas *(do gabarito)*

| peça | ideia |
| --- | --- |
| `Value[C] = C match { case Column[n, a] => a }` | um caso, sem alternativa: qualquer outra coisa fica sem reduzir e é erro onde for usada |
| `Values[Cs] = Tuple.Map[Cs, Value]` | a recursão sobre a tupla é a da biblioteca padrão |
| `run: List[Values[Cs]]` | o tipo da linha é calculado a partir do select, então não tem como divergir dele |

## Exercício 02 — só as colunas desta tabela

| peça | ideia |
| --- | --- |
| `where[N, A](column: Column[N, A])(value: A)` | o `A` já está na assinatura; não precisa de `Value[...]` |
| nomes não distinguem tabelas | `Users.id` e `Orders.id` têm o mesmo `N` e o mesmo `A`; o que difere é o prefixo do caminho |
| `<:<`, não `=:=` | uma coluna específica *cabe* em `Column[?, ?]`, não é *igual* a ele |
| `Tuple.Union[Cs] <:< Column[?, ?]` | uma união cabe em `T` só se cada membro couber: o "para todo elemento" numa só pergunta |
| `select(EmptyTuple)` | a união vazia é `Nothing`, que cabe em tudo |

**Perguntei:** `=:=` contra `<:<` — `=:=` quando o tipo precisa *ser*
exatamente aquele (um fato booleano, um estado final; um `Nothing` não pode
passar), `<:<` quando só precisa *caber*. E `trait` contra `abstract class`
para a `Table`: aqui não faz diferença, porque traits do Scala 3 recebem
parâmetros; `abstract class` diz "raiz de uma hierarquia".

## Exercício 03 — ler uma coluna de uma linha

| peça | ideia |
| --- | --- |
| `IndexOf` sem caso para `EmptyTuple` | qualquer número de "não achei" acaba somado e vira uma posição válida (o meu `-1` dava `1`); um tipo preso não |
| `IndexOf[...] <: Int` | o `+` de `ops.int` só aceita o que ele sabe que é `Int` |
| `ValueOf[IndexOf[Cs, Column[S, A]]]` | uma evidência faz dois papéis: só existe se a coluna estiver na linha, e o `.value` dela é a posição |
| `(column: Column[S, A])` antes do `using` | a lição do capítulo 22 de novo |
| procurar `Column[S, A]`, não `S` | o que se procura precisa ter a forma dos elementos da tupla |

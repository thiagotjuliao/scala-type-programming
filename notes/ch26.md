## Exercício 01 — um caminho cujo tipo lista o que captura

| peça | ideia |
| --- | --- |
| `/[A](capture: Capture[A]): Path[Tuple.Append[In, A]]` | a captura põe `A` no fim de `In`; no início (`A *: In`) os tipos sairiam invertidos, `(String, Int)` em vez de `(Int, String)` |
| `/(literal: String): Path[In]` | um literal não acrescenta nada à tupla |
| o tipo de `post` não é escrito em lugar nenhum | sai de quatro chamadas de `/`, cada uma calculando um `Tuple.Append` |
| `in.toList: List[Union[In]]` | dentro de `render`, `In` é abstrato e `Union[In]` não reduz, mas tudo é `Any`, que é o que `Capture.show` aceita |
| `foldLeft` carregando os valores que sobram | não dá `zip`: o literal não consome valor, a captura consome o próximo |
| `foldLeft` + `::` + `.reverse` | `foldRight` casaria a última captura com o primeiro valor: `ClassCastException` no cast de `show` |
| `mkString("/", "/", "")` | `/` entre as partes, não depois de cada uma; dá `"/"` para o root |
| `throw AssertionError(...)` no caso impossível | invariante minha, não erro de quem chama (`assert` para mim, `require` para o chamador); `???` diria "falta implementar" |
| `split("/").filter(_.nonEmpty)` | o `split` do Java mantém o `""` do início e descarta os do fim; `.tail` quebra em `"/"` (lista vazia) |
| `segments.length == parts.length` antes do `zip` | o `zip` corta no menor: `"/users/42"` casaria com `userPosts` |
| literal → `Some(ins)`, captura → `c.read(s).map(_ :: ins)` | só as capturas viram valores; o literal só confere |
| `Tuple.fromArray(...).asInstanceOf[In]` | `fromArray` devolve `Tuple`; o cast vale para a tupla montada, não para cada elemento, e só é seguro se a ordem estiver certa |

**Onde travei:** não achei `toList` porque procurei no `object Tuple` (os
métodos de conversão ficam no `trait`). Não vi o `""` inicial do `split`.
Coloquei os literais na lista de valores do `parse` e esqueci o `.reverse`
ali. Com duas capturas o tipo dizia `(Int, String)` e o valor era
`("hello", 42)`, e só o `assertEquals` pegou.

## Exercício 02 — o endpoint decide o tipo do handler

| peça | ideia |
| --- | --- |
| `type Args[In] = In match` com `EmptyTuple`, `t *: EmptyTuple`, `a *: b` | o tipo do handler é calculado a partir do caminho; o caso de um elemento vem antes do geral, senão `Tuple1` cairia em `a *: b` |
| `handle(f: Args[In] => Out)` | na chamada `In` e `Out` são concretos e `Args[In]` reduz; `(id: String)`, `Tuple1[Int]` ou o resultado errado não compilam. `Nothing => Any` aceitava tudo e não chamava nada |
| `Route` / `Router` | o `Router` só conhece strings; o `handle` é a ponte entre o handler tipado e `String => Option[String]` |
| `path.parse(url).map(in => codec.encode(f(toArgs(in))))` | o `None` do `parse` atravessa intacto e vira 404, sem chamar o handler; o `codec` transforma `Out` no corpo |
| `parse` dá `Some(Tuple1(1))`, não `Some(1)` | os literais só conferem; mesmo uma captura vem como tupla, e é isso que `Args` resolve |
| `toArgs` casando o valor caso a caso + `.asInstanceOf[Args[In]]` | o `match` sobre o valor não ensina nada ao compilador sobre o tipo `In`; dentro do `handle` `Args[In]` não reduz, e o cast declara a garantia (dá para fazer um cast só, no `match` inteiro) |
| `(a, EmptyTuple)` vs `a *: EmptyTuple` | o primeiro é um par; o `Tuple1` cairia no `case other` e daria `ClassCastException` |
| `inline` + `erasedValue[In]` | funciona onde `In` é concreto, mas num `Endpoint` genérico cai no `case _` sem aviso e quebra em tempo de execução (testado num probe) |

**Onde travei:** achei que o `run` devolvia o valor capturado (`Some(1)`) e
não o corpo da resposta; coloquei os literais dentro da tupla do `parse` de
novo; escrevi o padrão de um elemento como par.

## Exercício 03 — um cliente a partir dos mesmos valores

| peça | ideia |
| --- | --- |
| `call(e: Endpoint)(args: Args[e.In]): Either[String, e.Out]` | dependent method type: os argumentos e o resultado vêm do valor `e`; em `call(userName)(1)`, `Args[e.In]` é `Int` e `e.Out` é `String` |
| duas listas de parâmetros | estilo: em Scala 3.9.0 `(e: E, args: e.In)` numa lista só também compila (testado) |
| `tuple(path, args)` | o inverso de `Args.of`: as capturas de `parts` decidem o caso, o `args` dá o valor |
| `args *: EmptyTuple` | o `Tuple1(args)`, com o mesmo `*:` do match type |
| `e.method`, `e.path.render`, `e.codec.decode` | o cliente não repete nada: método, caminho e formato vêm do mesmo valor que o servidor usou |
| `.toRight(...)` | `Option` para `Either`: status ≠ 200 e corpo ilegível viram valores, não exceções |

**Onde travei:** no `tuple` devolvi as próprias capturas (`h` era o
`Capture[Int]`, não o `1`), e o cast escondeu; o `args` nem aparecia no corpo.

## Exercício 04 — o caminho escrito como string

| peça | ideia |
| --- | --- |
| `StringContext("/users/", "/posts/", "")` | o texto é cortado só nos `$`, com as barras dentro das partes; partes = argumentos + 1, e o argumento `i` fica entre `texts(i)` e `texts(i + 1)` |
| `Varargs` + `valueOrAbort`, com `case _` | abrem o `StringContext` e os argumentos como código; sem o `case _` o `match` lançaria `MatchError` dentro do compilador |
| `texts.head.startsWith("/")` | só a primeira parte é o começo da string; `path"$id/users"` tem primeira parte `""` e já é recusado |
| `contains("//")` em cada parte | uma captura fica sempre entre partes, então um `//` nunca atravessa uma captura |
| `split("/")` + `find` | a mensagem mostra o segmento, não a parte; `isLetterOrDigit` aceita `é` (escolha consciente) |
| `texts.zip(texts.tail)` | um par por argumento: termina com `/` antes, começa com `/` ou é vazio depois |
| `report.errorAndAbort`, nunca `???` nem `assert` | a macro roda dentro do compilador; qualquer exceção vira crash, até a invariante impossível |
| `widen.show(using Printer.TypeReprShortCode)` | `n.type` vira `Int`, `scala.Int` vira `Int`: o tipo como escrito |
| `zipAll(arguments.map(Option(_)), "", None)` | "não há argumento" no tipo; um `'{ () }` cairia no "só Capture" e um `Capture` falso mudaria o `In` |
| `Either[String, Expr[Any]]` | padrão citado só se aplica ao que o compilador sabe ser `Expr`; numa lista `String | Expr` ele recusa |
| `'{ $p: Path[t] }` + `'{ $cap: Capture[a] }` no passo do `fold` | os tipos são ligados onde são usados; guardado numa lista o `a` se perde. Não se extrai o `Capture`: o `Expr` é encaixado com splice, `'{ $p / $cap }` |
| `foldLeft[Expr[Path[?]]]('{ Path.root })` | deduzido de `Path.root`, o acumulador seria `Path[EmptyTuple]` para sempre |
| type test `c: Expr[Capture[?]]` | não testa nada (erasure) e gera `Reference to _ within quotes requires a given scala.quoted.Type[_]` (testado) |
| `transparent` | a chamada tem o tipo do código expandido, `Path[Int *: EmptyTuple]`, não o `Path[?]` declarado |

**Onde travei:** cortei a string pelas barras em vez dos `$`; juntei
segmentos com `replace` e depois com `mkString`; quis tirar o `Capture` de
dentro do `Expr`; esqueci o tipo do acumulador do `fold`.

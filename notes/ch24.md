# Capítulo 24 — Derived JSON codec

Minhas notas sobre o que cada exercício ensinou. Reconstruídas em 2026-10-13 a
partir das sessões de 2026-10-08 a 2026-10-12.

## Exercício 01 — `Encoder.derived`

| peça | ideia |
| --- | --- |
| nome, encoder e valor | os dois primeiros saem do `Mirror` na compilação; o valor só existe em runtime, via `productIterator` |
| `summonFrom`: encoder pronto antes do `Mirror` | `Option` e `List` também têm mirror; derivar primeiro codificaria `Some("ada")` como um objeto com `"type": "Some"` |
| `lazyZip`, não `for` | três geradores fazem todas as combinações |
| encoders por nome, sem `val` no `derived` | o encoder de um tipo recursivo precisa de si mesmo; avaliado na criação, ele se lê antes de existir — foi isso que travou o servidor do sbt |
| `lazy val encs` dentro do `def` | calculado uma vez, no primeiro `encode` |
| `encoderProduct` / `encoderSum` como `def` comum | a classe anônima da lambda seria copiada em cada derivação |
| `ordinal` | a posição do caso escolhe o nome e o encoder pelo mesmo índice |
| `match` no `JObject` do caso | `Json` não promete um objeto, então o `"type"` só entra na frente depois do match |

## Exercício 02 — `Decoder.derived`

| peça | ideia |
| --- | --- |
| `fromProduct`, não `fromTuple` | valores montados em runtime como `List[Any]` só formam um `Tuple`; `fromTuple` exige o tipo exato |
| campo ausente decodifica `JNull` | a derivação não sabe se o campo é opcional; o decoder do campo sabe |
| `"missing"` no lugar da mensagem do decoder | para um campo ausente, "expected a whole number" engana |
| `label :: e.path` | o caminho é montado de dentro para fora; cada nível põe o próprio nome na frente |
| `foldRight` com `for` sobre `Either` | um `for` tem número fixo de `<-`; o fold combina um campo com o resto e para no primeiro erro |
| `lazy val` fora do `json => ...` | dentro da função, seria recalculado a cada `decode` |
| a posição do caso vem do `"type"` | ainda não existe valor para chamar `ordinal` |
| o objeto inteiro vai para o decoder do caso | o decoder de produto só procura os próprios nomes de campo, então o `"type"` é ignorado |

**Onde travei:** `:+` no lugar de prepend no caminho; um `???` sobrando depois
do `inline match`, que virava o resultado; e `"unknown case Triangle"` escrito
como constante — a spec só testava esse nome.

## Exercício 03 — um erro de compilação que diz o tipo e o campo

| peça | ideia |
| --- | --- |
| `@implicitNotFound` no trait | um `summon[Encoder[Instant]]` simples busca a mensagem no tipo que está procurando |
| `case _ => error(...)` no `summonFrom` | um caso que não acha nada simplesmente não casa — sem mensagem; sem último caso, o erro é o genérico do `summonFrom` |
| `MirroredLabel` contra `MirroredElemLabels` | o nome do próprio tipo contra os nomes dos campos |
| `instances[T, Ts, Ls]` casando `(Ts, Ls)` | o `instance` só conhece `H` (aqui `Instant`); o nome do pai e o do campo descem pela recursão como tipos literais |
| `"..." + constValue[T] + "..."` | `error` precisa de uma constante; `constValue` de um tipo literal é uma, e a concatenação é dobrada |
| `Meeting` reporta `Event` | `Event` é derivado no caminho, como campo; o erro aponta onde a expansão parou |

**Onde travei:** achei primeiro que o `@implicitNotFound` do trait apareceria
dentro da derivação. E faltou um espaço: `fieldathas` — a spec compara o
começo da mensagem exatamente.
